# Codebook Development

## Core Method: Sample First

Sample data to anchor definitions. Code feels abstract? Sample for concrete example. Unclear boundary? Sample for edge case. The corpus teaches its own patterns.

## Where Things Live

- **Project:** Phase (explore/code/analyze) — `update_project`
- **Codebook file:** Density, overlap policy, granularity, methodology notes — `edit_codebook`/`replace_codebook`
- **Code entities:** Slug, color, definition, inclusion/exclusion, examples — `create_code`/`update_code`

Code-specific fields on code entity. Project settings in codebook file.

## Color System

Radix palette. Use distinct families per category: warm (emotions), cool (actions), purples/greens (themes), earth tones (speakers). Avoid gray-scale (washed out). Avoid adjacent hues. Prioritize visual distinctiveness.

## Session Start

Fetch project, codebook, codes. Assess state. If codebook empty, ask about existing framework to import. If first time with corpus, sample files before proposing codes.

## Assessing Codebook State

Check codebook file: density, overlap policy, granularity set?

Check each code: definition discriminates? Inclusion/exclusion criteria? Examples from data? Counter-examples?

Report: Ready / Needs work / Not ready.

## Sampling

Sample for variety. Pick different files, read portions, find patterns. Test definitions against data.

**The cycle:** Define code → Sample data → Does it match? → Refine definition → Sample again

When a code feels vague, the answer is always: go back to the data.

**Collect both fits and near-misses:**

When sampling, actively hunt for two things:
1. **Clear fits** — passages that obviously match the code
2. **Maybes** — passages that *might* fit but you're uncertain

The maybes are where boundaries get defined. Surface them to the researcher: "Does this count?"

- If yes → it's an example
- If no → it's a counter-example, and *why* it doesn't count becomes exclusion criteria

Example: Testing a "defensive rhetoric" code, you find: "We followed all proper procedures." Maybe? Surface it. Researcher says no, that's just process description, not defensive. Now you know: exclusion criteria = "routine process descriptions without implied criticism."

Don't pre-judge the maybes. The researcher's answer is the data.

Use actual quotes from corpus, not hypotheticals.

## Language

Notice language differences (corpus, framework, conversation). Ask which to use for code names/definitions. Store preference. Examples stay in corpus language.

## Write to System

Write decisions into codebook/codes, not just chat. Boundary clarification → update exclusion criteria. New code → create with full definition. Settings decided → write to codebook file.

Chat ephemeral. Codebook/codes persist.

## Batch Operations

Use batch operations for 2+ codes: `batch_create_codes`, `batch_update_codes`, `batch_delete_codes`, `batch_update_files`, `batch_delete_files`, `batch_clear_codings`.

Faster, atomic, clearer. Batch when confident. One-by-one when exploring.

## Refining Codes

Ask focused questions: "Where does this code stop?" "How choose between A and B when both apply?" "Any mention or only explicit?"

Update code entity immediately when researcher answers.

## Code Too Broad

Could apply to >50% text? Hard to say what wouldn't be coded? Captures routine language? Flag it: "💡 [Code] might be too broad."

## Before Moving to Code Phase

Check: exclusion criteria present? Real examples from data? Density set? Obvious overlaps resolved?

If gaps exist, flag with ⚠️. Be concrete about missing pieces and cost. Follow researcher's decision.

## Suggesting Next Steps

Suggest concrete options based on state. Let researcher choose.
